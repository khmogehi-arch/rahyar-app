# راهیار — MVP

پیاده‌سازی فاز ۱ راهیار طبق «سند مشخصات فنی پیاده‌سازی — راهیار MVP»: مسیریابی گام‌به‌گام داخل
ساختمان با یک اسکن QR در ورودی، بدون موقعیت‌یابی زنده و بدون وابستگی به هیچ پلتفرم IPS (مثل
Situm/Mapxus). این پروژه دقیقاً طبق بخش ۷ آن سند («خارج از دامنه») ساخته شده و هیچ‌کدام از موارد
زیر را ندارد:

- موقعیت‌یابی زنده / نقطه آبی متحرک
- یکپارچه‌سازی با SDK سیتوم، Mapxus یا هر پلتفرم IPS دیگر
- واقعیت افزوده (AR)
- اپ نیتیو iOS/Android
- نقش‌های کاربری پیچیده یا چندسطحی (فقط یک سطح دسترسی کارمند)

## ساختار پروژه

سه بخش، روی یک بک‌اند مشترک و یک پایگاه داده یکسان:

```
backend/        API واحد (Express + Postgres) — هر دو اپ از آن استفاده می‌کنند
admin-panel/    اپ الف: پنل داخلی تیم (React, وب مرورگر دسکتاپ)
visitor-app/    اپ ب: وب‌اپ مراجعه‌کننده (React, PWA-ready, موبایل)
```

مدل داده طبق بخش ۳ سند: `Building`, `Floor`, `Node` (ورودی/مقصد/تقاطع/آسانسور), `Edge` (یال
جهت‌دار با فاصله واقعی و دستورالعمل), `QRCode`, `Beacon`, `Destination`.

## دیپلوی رایگان روی Vercel (بدون نصب چیزی، فقط با مرورگر)

هر سه بخش برای دیپلوی روی Vercel آماده‌سازی شده‌اند (`vercel.json` و `backend/api/index.js` در
پروژه موجود است). چون Vercel سه بخش این پروژه را به‌صورت سه پروژه جدا می‌شناسد، باید هرکدام را
جداگانه از همین ریپازیتوری وارد (Import) کنید — **به همین ترتیب**، چون هرکدام به آدرس بخش قبلی
نیاز دارد:

### ۱. بک‌اند (اول این یکی)

روی [vercel.com](https://vercel.com) با اکانت گیت‌هاب وارد شوید → **Add New → Project** → همین
ریپازیتوری را انتخاب کنید → **Root Directory** را روی `backend` بگذارید → قبل از زدن Deploy، این
Environment Variables را اضافه کنید:

| کلید | مقدار |
|---|---|
| `JWT_SECRET` | یک رشته تصادفی دلخواه (مثلاً از یک پسورد-جنریتور) |
| `ADMIN_USERNAME` | نام کاربری دلخواه برای ورود کارکنان، مثلاً `admin` |
| `ADMIN_PASSWORD` | رمز عبور دلخواه |

Deploy بزنید. سپس، **قبل از استفاده واقعی از پنل**، این دو مرحله را روی همین پروژه (بک‌اند) در
داشبورد Vercel انجام دهید — این‌جاست که داده‌ها واقعاً پایدار می‌شوند:

1. تب **Storage** → **Create Database** → **Neon (Postgres)** → به پروژه بک‌اند وصل کنید. Vercel
   خودش `DATABASE_URL` (یا `POSTGRES_URL`) را به Environment Variables پروژه اضافه می‌کند —
   نیازی به کپی/پیست دستی connection string نیست.
2. تب **Storage** → **Create** → **Blob** → به همین پروژه وصل کنید. این هم `BLOB_READ_WRITE_TOKEN`
   را خودکار اضافه می‌کند — بدون این، آپلود تصویر پلان روی Vercel کار نمی‌کند چون فقط `/tmp`
   قابل‌نوشتن است و بین اجراها پاک می‌شود.

بعد از این دو مرحله، پروژه بک‌اند را یک‌بار **Redeploy** کنید تا env varهای جدید اعمال شوند. آدرس
نهایی (چیزی شبیه `https://rahyar-backend-xxxx.vercel.app`) را یادداشت کنید — این را در ادامه
**BACKEND_URL** می‌نامیم.

### ۲. وب‌اپ مراجعه‌کننده (دوم)

دوباره Add New → Project → همان ریپازیتوری → **Root Directory** روی `visitor-app` (Vercel خودش
فریم‌ورک Vite را تشخیص می‌دهد). قبل از Deploy، Environment Variable زیر را اضافه کنید:

| کلید | مقدار |
|---|---|
| `VITE_API_URL` | همان BACKEND_URL مرحله قبل (بدون `/` انتهایی) |

Deploy بزنید و آدرس نهایی را یادداشت کنید — **VISITOR_URL**.

### ۳. پنل داخلی تیم (سوم)

دوباره Add New → Project → همان ریپازیتوری → **Root Directory** روی `admin-panel`. این Environment
Variables را اضافه کنید:

| کلید | مقدار |
|---|---|
| `VITE_API_URL` | همان BACKEND_URL |
| `VITE_VISITOR_APP_URL` | همان VISITOR_URL مرحله قبل |

Deploy بزنید. آدرس نهایی این پروژه همان لینکی است که با مرورگر باز می‌کنید و با
`ADMIN_USERNAME`/`ADMIN_PASSWORD` که در مرحله ۱ تعریف کردید وارد می‌شوید.

### نکته مهم درباره ماندگاری داده روی این نوع دیپلوی

بک‌اند روی Vercel به‌صورت Serverless اجرا می‌شود و فقط پوشه `/tmp` قابل‌نوشتن است — این پوشه بین
فراخوانی‌ها/بعد از هر Cold Start پاک می‌شود و بین instance های مختلف مشترک نیست. به همین دلیل
دیتابیس (SQLite) و تصاویر آپلودشده دیگر روی فایل‌سیستم محلی بک‌اند ذخیره نمی‌شوند: دیتابیس روی
Postgres (Neon) و تصاویر روی Vercel Blob ذخیره می‌شوند — هر دو یک سرویس شبکه‌ای مستقل از فایل‌سیستم
instance، پس بین فراخوانی‌ها و Cold Startها ماندگار می‌مانند. **اگر مرحله‌ی «Storage → Create
Database/Blob» بالا انجام نشود**، بک‌اند بدون `DATABASE_URL` روی Vercel اصلاً بالا نمی‌آید (هر
درخواست خطای پیکربندی می‌گیرد) و بدون `BLOB_READ_WRITE_TOKEN` آپلود تصویر پلان شکست می‌خورد.

### Keep-alive هفتگی برای Neon

بک‌اند یک Vercel Cron Job دارد (`backend/vercel.json`) که هفته‌ای یک‌بار `GET /api/cron/keepalive`
را صدا می‌زند تا یک کوئری سبک به دیتابیس بزند. این کار مخصوصِ suspend شدنِ عادیِ compute بعد از چند
دقیقه بی‌فعالیتی نیست (آن خودش طی چند ثانیه و با retry موجود در `db.js` بی‌سروصدا حل می‌شود)، بلکه
جلوی ریسکِ دورتر را می‌گیرد: پروژه‌ی Neon که هفته‌ها/ماه‌ها هیچ ترافیکی نبیند ممکن است طبق قوانین پلن
Free غیرفعال/بازنشانی شود. برای امن‌کردن این endpoint در برابر صدا زدن عمومی، یک مقدار تصادفی
(مثلاً خروجی `openssl rand -hex 32`) را به‌عنوان `CRON_SECRET` در Environment Variables پروژه
بک‌اند روی Vercel اضافه کنید — Vercel خودش این مقدار را هنگام اجرای Cron Job به‌صورت
`Authorization: Bearer $CRON_SECRET` می‌فرستد.

## راه‌اندازی برای توسعه (به‌صورت محلی)

### ۱. بک‌اند

```bash
cd backend
npm install
cp .env.example .env      # مقادیر JWT_SECRET، ADMIN_PASSWORD و DATABASE_URL را تنظیم کنید
npm run seed              # ساخت کاربر کارمند اولیه (رمز عبور ساده)
npm run dev                # http://localhost:4000
```

برای `DATABASE_URL` به یک Postgres نیاز دارید — ساده‌ترین گزینه یک دیتابیس رایگان روی
[neon.tech](https://neon.tech) است (همان که در بخش دیپلوی Vercel استفاده می‌شود)؛ یک Postgres
محلی هم کار می‌کند. جدول‌ها خودکار در اولین اجرا ساخته می‌شوند — نیازی به migration دستی نیست.
بدون تنظیم `BLOB_READ_WRITE_TOKEN`، آپلود تصویر پلان به‌صورت محلی در پوشه `backend/uploads`
ذخیره می‌شود.

### ۲. پنل داخلی تیم (اپ الف)

```bash
cd admin-panel
npm install
cp .env.example .env
npm run dev                # http://localhost:5173
```

با نام کاربری/رمز عبور تعریف‌شده در `backend/.env` وارد شوید. سپس به ترتیب: ساختمان و طبقه
بسازید، پلان طبقه را آپلود و مقیاس‌بندی کنید (کلیک دو نقطه با فاصله واقعی معلوم)، در «ویرایشگر
نقشه» نقاط (Node) و یال‌ها (Edge) را ترسیم کنید، برای نقاط ورودی کد QR بسازید، و مقاصد را برای
نمایش در اپ مراجعه‌کننده ثبت کنید.

### ۳. وب‌اپ مراجعه‌کننده (اپ ب)

```bash
cd visitor-app
npm install
cp .env.example .env
npm run dev                # http://localhost:5174
```

آدرس هر کد QR تولیدشده در پنل داخلی چیزی شبیه `http://localhost:5174/entry/<token>` است — دقیقاً
همانی که مراجعه‌کننده با اسکن QR درب ورودی باز می‌کند. صفحه اول اسکن را resolve می‌کند، سپس صفحه
انتخاب مقصد و در نهایت مسیر گام‌به‌گام (محاسبه‌شده یک‌باره، بدون رهگیری زنده) نمایش داده می‌شود.
دکمه «مسیر را گم کردم» کاربر را به انتخاب مقصد بازمی‌گرداند.

## نکات پیاده‌سازی

- **مسیریابی**: الگوریتم Dijkstra ساده روی گراف Node/Edge، فقط در لحظه انتخاب مقصد اجرا می‌شود
  (`backend/src/utils/dijkstra.js`) — بدون GPS، بلوتوث یا هیچ درخواست دسترسی موقعیت مکانی.
- **بیکن**: صفحه «بیکن‌ها» در پنل داخلی صرفاً ثبت UUID/Major/Minor در دیتابیس و اتصال آن به نقطه
  آسانسور است؛ هیچ اسکن BLE یا موقعیت‌یابی زنده‌ای در کد پیاده‌سازی نشده (طبق بخش ۷، این ویژگی
  عمداً کنار گذاشته شده).
- **احراز هویت**: ورود ساده با رمز عبور برای کارکنان (JWT)، بدون نقش‌های چندسطحی. وب‌اپ
  مراجعه‌کننده اصلاً فرم ورود ندارد — فقط با اسکن QR باز می‌شود.
- **PWA**: وب‌اپ مراجعه‌کننده دارای `manifest.json` و آیکون است و از طریق «Add to Home Screen» در
  مرورگر قابل نصب است؛ به SDK یا مجوز موقعیت‌یابی نیازی ندارد.
- **پایگاه داده**: Postgres (از طریق `DATABASE_URL`، مثلاً Neon) — لایه دیتابیس در
  `backend/src/db.js` است و جدول‌ها را خودکار در اولین اتصال می‌سازد.
- **تصاویر پلان**: در production روی Vercel Blob (`BLOB_READ_WRITE_TOKEN`) ذخیره می‌شوند؛ بدون آن
  (مثلاً در توسعه محلی) در `backend/uploads` نوشته می‌شوند — منطق انتخاب در `backend/src/storage.js`.
